# S3 backend

A repository can live in an S3 bucket instead of a directory. Every
command accepts `--repo s3://bucket[/prefix]`.

```sh
export AWS_ACCESS_KEY_ID=... AWS_SECRET_ACCESS_KEY=... AWS_REGION=us-west-2
gpuckpt init     --repo s3://my-ckpts/train-42
gpuckpt snapshot --repo s3://my-ckpts/train-42 --pid 12345 --resume
gpuckpt list     --repo s3://my-ckpts/train-42
gpuckpt restore  --repo s3://my-ckpts/train-42 --pid 12345 --snapshot ID
gpuckpt gc       --repo s3://my-ckpts/train-42            # see "gc and the grace period"
```

## Configuration

| Variable | Meaning |
|----------|---------|
| `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` | Required. Static credentials only; instance profiles, SSO and the credentials file are not read. |
| `AWS_SESSION_TOKEN` | Optional; sent and signed as `x-amz-security-token`. |
| `AWS_REGION` / `AWS_DEFAULT_REGION` | Signing region. Default `us-east-1`. |
| `GPUCKPT_S3_ENDPOINT` | `http(s)://host[:port]` for MinIO, Ceph RGW, or a mock. Default `https://s3.<region>.amazonaws.com`. |
| `GPUCKPT_S3_PATH_STYLE` | `1` = `/bucket/key`, `0` = `bucket.host/key`. Default `1` when an endpoint is set, `0` otherwise. |
| `GPUCKPT_S3_RETRIES` | Retries for network errors, 429 and 5xx. Default 4, exponential backoff from 200 ms. |
| `AWS_CA_BUNDLE` | TLS trust file passed to libcurl. |

The client is libcurl plus an in-tree AWS Signature Version 4 signer
(`src/s3.c`); there is no AWS SDK dependency. `gpuckpt version` prints
`s3: libcurl` when the backend is compiled in and `s3: unavailable` when
libcurl headers were missing at build time, in which case `s3://` repos are
refused with that reason.

## Layout

Keys are identical to the local layout:

```
<prefix>/config
<prefix>/chunks/<hh>/<sha256>
<prefix>/snapshots/<id>.manifest
```

So `aws s3 sync /local/repo s3://bucket/prefix` (excluding `lock` and
`tmp/`) produces a valid S3 repository, and syncing the other way produces
a valid local one. The test suite checks this by uploading a local repo
key-for-key and verifying it through the S3 path.

## Write-once on S3

Chunks and manifests are published with `PUT` + `If-None-Match: *`. S3
answers 412 when the key already exists, which the client reports as
"already present": exactly one of N concurrent writers of the same chunk
counts it as new, matching the `link(2)` behaviour of the local store.
Conditional writes are supported by AWS S3 (since August 2024) and by
current MinIO and Ceph RGW; an endpoint that ignores the header still
stores correct bytes (same content, same key) but over-counts `chunks_new`
and loses manifest immutability.

## gc and the grace period

The local store takes an exclusive `flock` during `gc`, so no snapshot can
be deduplicating against a chunk that `gc` is about to delete. S3 has no
lock. Instead, `gc` leaves unreferenced chunks whose `LastModified` is
younger than `--grace-seconds` (default 3600 on S3, 0 locally) in place. A
snapshot that skipped writing a chunk because it already existed therefore
has an hour to publish the manifest that references it. Run `gc` with
`--grace-seconds 0` only when no snapshot can be in flight.

`forget` deletes a manifest immediately in both backends.

## Performance notes

- Every chunk is one HTTP request. The S3 path defaults to 16 worker
  threads (local: up to 8) because it is latency-bound; raise `--threads`
  for high-bandwidth links. Larger `--chunk-size` at `init` reduces request
  count proportionally.
- Dedup checks are a `HEAD` per chunk before the `PUT`; on a 100% new image
  that doubles the request count. It is kept because a `PUT` that will be
  refused still uploads the body first.
- Restore and verify re-download every chunk; there is no local cache.
- A local repo mirrored to S3 (sync after each snapshot) is the lowest-pause
  configuration: the checkpoint itself runs against local disk and the
  upload happens after `complete` has released the target, which is the
  "export only after an immutable copy exists" ordering the plan requires.

## Not supported

Credential providers other than environment variables, multipart upload
(a chunk is one object; chunk sizes above 5 GB are refused by S3), object
versioning or lifecycle interactions, server-side encryption headers, and
requester-pays buckets.
